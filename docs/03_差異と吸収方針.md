# 03 VBとWeb版の差異と吸収方針

イシュー #3 の懸念点「差異を洗い出し、Web版の側で吸収する」への回答です。
基本方針は **VB の業務ロジックの意味を変えない**。VBとWebの仕組みの違いは、Web版の側（API・画面）で吸収します。
VBの不具合と思われる箇所は、**勝手に直さず**「VBの挙動／Web版での扱い（案）」を並べ、実装する画面の着手時に確認します（技術的な画面の実装順は [04](04_移行の進め方.md)）。

## 1. 仕組みの差異と吸収方針

| ID | 観点 | VB（Windows Forms） | Web版 | 吸収方針 |
| --- | --- | --- | --- | --- |
| D-01 | 画面の遷移 | フォームを `Show`／`Close`。同じ画面は1つだけ開く | URLごとの画面（React Router） | 画面ごとにルートを定義。重複起動の制御は不要 |
| D-02 | ログイン状態 | モジュール変数（`Login_info`・`kengen`・`Login_ID`）に保持 | HTTPセッション（Cookie）に保持 | サーバー側セッション。画面の出し分けとAPIの認可の**両方**で権限を確認 |
| D-03 | 権限制御 | ボタンの有効・無効のみ | 画面の非表示＋API側の拒否 | APIで必ず権限を検査（VBは画面側のみ） |
| D-04 | DB接続 | アプリ全体で1接続（シングルトン）。トランザクションも1つ | 接続プール。リクエストごとにトランザクション | `@Transactional` で画面操作（1リクエスト）＝1トランザクション。VBの `BeginTransaction`〜`Commit` の範囲と一致させる |
| D-05 | SQLの組み立て | 文字列連結（入力値をそのままSQLに埋め込む） | プレースホルダ（`PreparedStatement` / `NamedParameterJdbcTemplate`） | **全て置き換える**。SQLの意味（条件・結合・並び）は変えない |
| D-06 | 日時の取得 | `NOW()` をSQLで呼ぶ。VBの時計は画面表示用 | `NOW()` をSQLで呼ぶ（DB時刻）／時計表示はブラウザ | 登録日時はVBと同じくDB時刻。ブラウザの時刻は表示のみ |
| D-07 | 日時の表示 | `DataRow.ToString`（ロケール依存の書式） | JSON（ISO 8601）→ 画面で整形 | 画面の表示書式は「yyyy年MM月dd日 HH:mm:ss」に統一（時計と同じ） |
| D-08 | 一覧表示 | DataGridView（全件を読み込み） | 表（HTMLテーブル） | まず全件表示を再現。件数が増える場合はページングを検討（意味の変更になるため、確認してから） |
| D-09 | 確認ダイアログ | `MessageBox`（はい／いいえ） | モーダル | 画面側で確認後にAPIを呼ぶ |
| D-10 | エラー表示 | 例外メッセージをそのまま `MessageBox` | APIが「エラーコード＋日本語メッセージ」を返し画面が通知 | 業務メッセージ（例：「入力された棚番は存在しません。」）は文言をVBと同じにする。例外の中身は画面に出さない |
| D-11 | 画面内の計算 | `CellValueChanged` で出庫後在庫数を計算 | 画面（React）で計算 | 計算式は同じ（在庫数－出庫数）。サーバーでも検証 |
| D-12 | 入力値の検証 | ほぼ無い（桁数の `MaxLength` のみ） | 画面とAPIの両方 | まず MaxLength 相当を再現。追加の検証は意味の変更になるため確認の上で |
| D-13 | パスワードの保存 | 平文で保存・一覧に表示 | ハッシュ保存が望ましい | 既存データの移行とログイン判定に関わるため、ユーザー管理・ログインの着手時に確認（要確認事項） |
| D-14 | 接続情報 | INIファイルに接続情報 | 環境変数（`.env`・Compose）／Spring の設定 | 値はリポジトリに入れない。`.env.example` に項目名だけ |
| D-15 | 配備 | WinForms のexe | Spring Boot と React の単一デプロイ（Windows限定） | フロントをビルドして Spring Boot の `static` に載せる（[04](04_移行の進め方.md)） |

## 2. データ型の対応（.NET／VB → PostgreSQL → Java／TypeScript）

VBは Npgsql 経由で PostgreSQL を使っているため、DBの型はVB原本と同じです。差が出るのは、アプリ側の型です。

| 項目 | VB（.NET） | PostgreSQL | Java（Web版） | TypeScript |
| --- | --- | --- | --- | --- |
| 文字列 | `String` | `varchar(n)` | `String` | `string` |
| 整数 | `Integer`（`CInt`） | `integer` | `int` / `Integer` | `number` |
| 日時 | `DateTime` | `timestamp` | `LocalDateTime` | `string`（ISO 8601） |
| 真偽 | `Boolean` | `boolean` | `boolean` | `boolean` |
| NULL | `DBNull`（`ToString` で空文字になる） | `NULL` | `null`（`Optional` 等） | `null` |
| 取得結果 | `DataTable`／`DataRow` | 行 | DTO（`record`） | 型定義 |

| 書き方 | VB | Web版 |
| --- | --- | --- |
| 文字列連結 | `"..." & x & "..."` | プレースホルダ（`:x`） |
| 部分一致 | `LIKE '%x%'` | `LIKE '%' || :x || '%'`（ワイルドカード文字のエスケープも考慮） |
| 前方一致の棚番 | `LIKE 'x-%'`（列）、`LIKE '%-x-%'`（連）、`LIKE '%-x'`（段） | 同じ意味のまま、`tana_retu` などの列で検索する案もある（結果が同じことを比較して確認） |
| 日付の範囲 | `BETWEEN 'yyyy-MM-dd' AND 'yyyy-MM-dd'` | 同じ意味を保つ（`work_date` の型により、終了日の当日分が含まれるかが変わるため要確認） |
| 識別子 | 大文字小文字が混在（PostgreSQLが小文字に畳む） | 小文字に統一 |
| 数値のSQL埋め込み | `& txtUnitPrice.Text &`（文字をそのまま） | 数値型にパースして渡す（不正な入力はAPIで拒否） |

## 3. VB原本で気づいた問題（実装時の扱い）

「VBの挙動」は原本のコードから読み取ったもの。「Web版での扱い（案）」は着手時に確認します。機密の値は含みません。

| ID | 画面 | VBの挙動 | Web版での扱い（案） |
| --- | --- | --- | --- |
| V-01 | ログイン | `M_user` 全件を回し、IDの一致とパスワードの一致を別々に判定する。別ユーザーのパスワードでも、存在するIDなら通る | ID＋パスワードの組で判定（意図は明らか）。意味が変わるので着手時に確認 |
| V-02 | 全般 | 入力値をSQLに直接連結（SQLインジェクションの危険）。`GetSqlValue` はあるが使われていない | プレースホルダで必ず防ぐ（D-05） |
| V-03 | 入庫 | 登録時の「在庫あり」判定が、ループの最後の行の結果で決まる（途中でヒットしても後続行で false に戻る） | 商品コードの在庫を直接検索して判定（意図どおりに実装） |
| V-04 | 入庫 | 既存在庫を積み増す UPDATE は棚番を見ない。新規 INSERT 後の `M_location` の UPDATE は `SET tana_status`（値なし）で文法が壊れており、`WHERE product_CD`（棚テーブルに無い列）。実行すると例外 | 意図は「入庫した棚の状態を 実棚 にする」と推測。着手時に確認 |
| V-05 | 入庫・出庫・在庫修正 | `T_jisseki` へ書き込む処理が無い。実績照会は読むだけ | 入庫・出庫・修正・削除で実績を記録する（区分の値は画面の選択肢と同じ）。意味の追加のため確認 |
| V-06 | 実績照会 | ユーザー名の条件が `LIKE '&名前%'`（先頭に `&` が入る誤記）。ユーザー名で絞るとほぼ0件 | 前方一致（`名前%`）にする案 |
| V-07 | 商品メンテナンス | 更新のSQLが文法不正（`productCD = '…'` の後に引用符の誤り。列名も `productCD`） | `product_cd`、`product_name` などの正しい列で更新 |
| V-08 | 在庫修正 | 修正・削除の条件が `product_CD` のみ（`stock_id` ではない）。同じ商品の在庫行が複数あると全てが対象 | `stock_id` で更新（1商品1棚の前提では結果は同じ） |
| V-09 | メインメニュー | 「クイック」ボタンが認証なしで全ボタンを有効化。ログアウトでログインIDを消さない | 開発用機能として移行しない案（確認） |
| V-10 | ロケーション | 一覧クリックの判定が `rowIndex > 0`（先頭行を選べない） | 先頭行も選べる（`>= 0`、他画面と同じ） |
| V-11 | 商品メンテナンス | 削除時、在庫行が無い商品は `dt.Rows(0)` で例外。在庫ありのときは Rollback 後も処理を続け最後に Commit を呼ぶ | 在庫行が無ければ削除可、在庫があれば全体を取り消す |
| V-12 | 入庫・出庫・在庫検索 | 商品コードの入力上限が画面ごとに違う（8または9桁） | 8桁に統一する案（入庫は8桁で検索しているため） |
| V-13 | ロケーション | 列・連・段の桁そろえ（ゼロ埋め）規則が無い。棚番の重複チェックも画面に無い | 主キー制約に任せ、重複はエラー表示 |
| V-14 | 入庫 | 追加欄の削除で、選択行数に関係なく件数を -1 する。選択無しでも -1 | 件数は表の実際の行数から出す |
| V-15 | 在庫修正 | 理由が空でもロールバックせず Commit を呼ぶ（変更が無いので実害なし）。理由は実績に記録されない | V-05 とあわせて、理由を実績の備考に記録する案 |
| V-16 | 全般 | カテゴリ・区分の一覧を各フォームに直書き（重複定義） | サーバーで1か所に定義 |

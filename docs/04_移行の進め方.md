# 04 移行の進め方（画面ごとの実装順の案）

イシュー #3 の懸念点「機能単位に分け、段階的にPRを出す」「別リポジトリのVBを参照する」への回答です。

## 1. 進め方の原則

1. **1つの機能（画面）＝1イシュー＝1PR**。イシュー #3 は「土台」までとし、各画面は別イシューで進める。
2. VB原本は**別フォルダ・別リポジトリのまま**参照する。このリポジトリには原本を入れず、必要な事実（SQLの意味・業務ルール・メッセージ文言）を `docs/` に日本語で書き写す。
3. 各画面の実装前に、`docs/` の該当節（[01](01_機能・画面一覧.md)）と、気づいた問題（[03](03_差異と吸収方針.md) の V-xx）を確認し、**意味が変わる点は実装前に確認する**。
4. 各画面の完了は「VBと同じ入力で、同じ結果が出る」ことで判断する（元プログラムとの動作比較）。比較した条件と結果をPRに残す。
5. 課題・判断は `docs/` に追記して残す（README の方針どおり）。

画面ごとに以下を1セットで進める：①API（Controller／Service／Repository）②画面（React）③VBとの動作比較④`docs/` の更新。

## 4. 目標の構成（案）

```
backend/    Spring Boot（Maven）。controller / service / repository を分離
frontend/   React + TypeScript（Vite）+ Tailwind CSS v4
dumps/      PostgreSQL のスキーマ・連番SQL（NNN_*.sql）
docs/       洗い出し・設計・差異・課題
```

単一デプロイ：`frontend` をビルドし、出力を `backend/src/main/resources/static` に置いて Spring Boot の1つの jar として配備する（Windows限定）。
今回はビルドの自動化（Maven のフロントビルドプラグインなど、依存の取得を伴うもの）は入れていない。着手時に決める。
